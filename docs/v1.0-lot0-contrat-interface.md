## 1. Objectif de parité

L'administration Halloween Map doit être immédiatement reconnue comme la même famille d'interface que le **back-office** LinKs : disposition, navigation, topbar, mode sombre/clair/système, typographie, surfaces, densité, boutons, filtres, cartes, tableaux, modales, formulaires, états et réactions. Elle contient néanmoins **ses neuf rubriques Halloween Map**, pas les menus Stories/codes promo/liens suivis de LinKs.

- **Logo** : `artwork/branding/halloween-map-wordmark-official.webp` dans la sidebar, et `artwork/branding/halloween-map-app-icon-official.webp` pour la variante compacte. Ces images sont les fichiers officiels déjà versionnés, **pas** un `PumpkinMark` recréé ou un texte de remplacement. Réutilisation technique de fichiers sous `artwork/` vers des assets Next.js publics à définir lors du lot de shell, sans altérer les originaux.
- **Séparation** : thème de back-office indépendant de la présentation publique Halloween Map. Le rendu du site public n'est pas un objet du chantier V1.0.
- **Autonomie** : pas d'adresse/connexion/admin central, pas de base ni d'authentification LinKs partagée.

### Grammaire visuelle à reprendre

- Sidebar : marque officielle + navigation avec icônes et états actifs + lien vers le site public + bas de panneau discret.
- Topbar : fil de contexte/breadcrumb et contrôle de thème ; contexte de saison à intégrer sans introduire deux en-têtes.
- Page : titre unique, description brève, actions contextuelles justifiées ; panneaux et formulaires avec espaces réguliers.
- Tableaux : header/tri explicites, recherche et filtres compacts, états vides utiles, pagination cohérente.
- Graphiques : une valeur et une unité lisibles ; données réelles seulement ; interaction clavier et pointer, légendes uniques.
- Formulaires : aide proche du champ, validation et enregistrement explicites, modifications non sauvegardées visibles et protégées.
- Menus/dialogues : mêmes tailles et feedbacks, focus restitué à la fermeture, confirmations pour les opérations destructrices.
- Animations : discrètes et désactivables par `prefers-reduced-motion`.

## 3. Arborescence cible proposée — à valider visuellement avant implémentation

Les entrées principales restent des capacités métier Halloween Map. Les groupes permettent la densité nécessaire sans introduire les fonctions inutiles de LinKs.

```text
[Logo officiel Halloween Map · by DomotiK Studio]

Tableau de bord
Statistiques

Gestion
  Maisons
  Utilisateurs
  Saisons

Communication
  Communications
  Activité

Configuration
  Contenus & documents
  Paramètres

[Voir Halloween Map]   [Version]
```

**À l'intérieur des modules** :
- **Maisons** : liste/filtres/fiche avec sections informations, modération, gestion, historique. Modales et actions issues des droits existants.
- **Saisons** : liste + création/réglages + actions très sensibles ; pas de faux « calendrier promo » LinKs.
- **Communications** : deux sous-espaces « Campagnes » et « Modèles de service » ; formulaires, aperçu, statut et éventuelle représentation chronologique justifiée.
- **Contenus & documents** : trois sections actuelles (« Textes de l'application », « Documents officiels », « Liens & contact ») ; sous-espaces cohérents avec le shell principal, pas de deuxième application imbriquée.
- **Paramètres** : groupes Événement, Localisation, Réglages avancés, Valeurs des futures saisons ; même fonction, exposition progressive.
- **Rôles/permissions** : gérés dans le parcours utilisateur existant, sans module additionnel vide.

**Mobile** : un même registre de navigation autorisée sur mobile et sur desktop, visible via menu compact/panneau repliable LinKs ; sous-menus conservés, saison/contextes et garde de brouillon protégés. Le branchement actuel de `Admin.tsx` entre mobile et desktop ne doit pas conduire à deux modèles métier divergents.

## 4. Catalogue initial des blocs à réutiliser

| Bloc logique | Référence LinKs | Dans Halloween Map aujourd'hui | Décision initiale |
| --- | --- | --- | --- |
| `AdminShell` | `admin/index.html`, `style.css` | `Admin.tsx`, `AdminBeta.css` | **Adapter** en composants React. Même apparence, logo officiel, menus métier |
| `AdminTheme` / tokens | `theme-init.js`, `style.css` | `Admin.tsx`, `Studio.tsx` | **Unifier** un seul thème de back-office ; ne pas inclure thèmes de la page publique LinKs |
| `Navigation` | `navigation.js` | `Admin.tsx` | **Adapter** ; une seule source des liens + permissions, React garde le state/routing |
| `Button/Input/Select/Dialog` | styles/états LinKs | `components/ui.tsx`, `common.tsx` | **Étendre** les primitives existantes au lieu de les dupliquer |
| `TableCollection` | `collection.js` | tables maisons/utilisateurs/saisons, `Pagination` | **Réutiliser les algorithmes génériques** ; adapter filtres et tri aux colonnes métier |
| `StudioCharts` | `charts.js` | `AdminStatistics`, `AttendanceChart` | **Adapter les patterns**, garder les calculs Halloween Map |
| `StudioCalendar` | `calendar.js`, `dates.js` | saisons/campagnes avec dates existantes | **Seulement si utile** ; ne pas créer un planning artificiel |
| `StudioEditor` | convention générale d'éditeur/back-office | `DocumentEditor` Tiptap et `VisualEditor` | **Adapter par contrat** : commandes, contenu, événements ; ne pas importer le droit juridique dans le cœur commun |
| `SaveStatus/DraftGuard` | feedback LinKs + garde upload | `Studio.tsx`, `useDraftGuard.ts` | **Conserver**, harmoniser les états ; garder la prévention de perte des brouillons |
| `MediaPicker/UploadGuard` | `uploads.js` | médias email/texte et fichiers existants | **Optionnel** si besoin réel ; pas de médiathèque LinKs créée sans usage |
| `AppSpecificAdapter` | aucun | services/API/permissions/saisons/SQL/worker | **Spécifique** à Halloween Map : ne jamais exposer en bloc fonctionnel générique |

Chaque bloc candidat doit avoir : API/props documentées, état de chargement/erreur/sauvegarde, tests d'accessibilité et de non-régression, possibilité de configuration et absence de dépendance cachée à l'autre application. **Pas de duplication de code ad hoc ni de surarchitecture de partage imposée au jalon V1.0.**

## 6. Décisions avant le premier changement de composants

1. Les composants UI en React sont propriétaires de leur cycle de vie ; les scripts impératifs LinKs ne sont pas injectés dans le DOM React.
2. Rester en **contrats et adaptateurs**, sans exiger aujourd'hui un paquet partagé public : LinKs reste en DOM/JS, Halloween en React. Les fonctions pures/tokens mutualisables seront identifiés progressivement.
3. Aucun changement des API/SQL/authentification, ni des données de collection, droits ou versions juridiques, dans les lots visuels.
4. Un seul shell et une seule topbar pour toute l'administration ; le thème isolé de `StudioShell` est un candidat à suppression **après** raccordement de l'éditeur au shell principal, jamais avant.
5. Chaque fonction métier a un chemin de navigation explicite et un test ; aucun bouton ajouté sans action.
6. Les composants non nécessaires à Halloween Map (codes promotionnels, CTR, raccourcis et liens de campagne LinKs, éditeur de thèmes publics LinKs) ne sont pas importés.
7. À chaque étape : comparaison contre [la matrice initiale](v1.0-lot0-fonctionnalites-et-regressions.md), relecture visuelle et tests ciblés avant de passer au lot suivant.
