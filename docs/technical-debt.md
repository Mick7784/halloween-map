# Dette technique conservée — V0.7.1

Relevé ciblé du Lot 3. Aucune modification de schéma, migration ou suppression DB. Les usages ci-dessous sont ceux du code local ; ils ne prouvent pas l’absence de consommateurs externes ou de données historiques sur une instance publiée.

| Élément / classement | Usage actuel | Doute et risque | Vérification future / recommandation |
| --- | --- | --- | --- |
| `reminder_deliveries` — probablement supprimable | Ancienne file de rappels, convertie vers `email_outbox` par migration 003. Encore nettoyée par la purge saisonnière. | Aucun expéditeur courant identifié ; des installations anciennes peuvent encore contenir des lignes. | Inventorier les lignes et versions déployées, confirmer la reprise des campagnes/outbox et l’absence de lecteurs externes. Préparer seulement ensuite une migration de retrait séparée. |
| `seasons.reminder_*` — à confirmer | Import historique vers les campagnes, nettoyage à la purge. `updateSeason` contrôle encore `reminder_enabled/reminder_at` avant de déplacer la purge. Le BO utilise les campagnes et leur calendrier. | Une valeur legacy peut encore bloquer un changement de purge (« La purge doit suivre le rappel programmé »). `reminder_recipient_estimate` est un alias de réponse calculé, distinct des anciennes colonnes. | Examiner les saisons migrées et campagnes relatives avant toute suppression. Isoler un éventuel correctif runtime avec test de régression ; aucune modification dans ce lot. |
| `roles.permissions` — probablement supprimable | Colonne requise par l’ancien schéma ; migration 004 vide ses valeurs. `getUser` calcule les capacités depuis les trois rôles fixes de `defaultRoles`. | Les API/exports ou anciens clients peuvent encore lire la colonne ; une suppression ne doit pas modifier les permissions métier. | Confirmer tous les lecteurs et écritures de création de rôle après publication réelle. Découpler les contrats historiques avant une migration dédiée. |
| `users.kind` — à confirmer | Valeurs STAFF/PARTICIPANT conservées à la création et exposées dans l’identité. L’autorisation courante dépend du rôle et du statut du compte. | Métadonnée d’identité encore dans les contrats ; absence de branche d’autorisation ne signifie pas absence de consommateur. | Vérifier comptes existants, API, exports et intégrations. Conserver tant que la compatibilité d’identité n’est pas démontrée. |
| `instances.plan` — à confirmer | Colonne contrainte COMMUNITY/PRO et type `Instance`; pas de facturation ou de sélection de fonctionnalités courante identifiée dans les zones examinées. | Peut être utilisée par un provisionnement externe ; supprimer la contrainte/colonne compromettrait ses écritures. | Inventorier provisionnement et sauvegardes d’instances ; décider dans un lot dédié, sans introduire une offre commerciale implicite. |
| `instances.config.flags/quotas` — à confirmer | Valeurs historiques dans le défaut JSON de configuration. Les limites actuelles de participation, routage et emails ont leurs propres règles. | Clés JSON potentiellement utilisées par un exploitant ou un ancien client ; ne pas confondre quotas fournisseur ORS et anciens paramètres d’instance. | Observer les configurations réellement déployées et vérifier les consommateurs externes. Documenter les clés avant un nettoyage ciblé. |
| Défaut SQL `participations.review_status='VALIDATED'` — à conserver pour compatibilité, à revoir | Migration 006. Les créations courantes écrivent explicitement PENDING en public et VALIDATED en BO autorisé ; une édition propriétaire REFUSED repasse PENDING. | Une écriture SQL ou intégration omettant le statut contournerait la modération publique. Modifier le défaut pourrait changer les imports historiques. | Rechercher tous les writers après publication et tester l’upgrade/import avant de proposer un défaut PENDING. Ne pas changer silencieusement la modération. |
| `/api/admin/stats`, `/api/admin/mail` — à confirmer | Routes de compatibilité conservées. Le BO courant utilise `dashboard`, `statistics` et `communications`. | Des clients déployés peuvent encore les appeler ; leur absence dans le shell courant ne suffit pas. | Confirmer l’absence de consommateurs après publication réelle, puis déprécier avant retrait. Conserver les contrôles d’accès et le blocage des emails TEST. |
| Géométrie/polyline et anciens parcours navigateur — à conserver | Contrats de routage et restauration des parcours historiques. ORS fournit l’estimation théorique ; la collecte libre utilise ses propres agrégats de progression. | Retirer les champs ou parseurs peut casser une reprise locale ou un ancien client. | Maintenir les tests de restauration. N’envisager un retrait qu’après une stratégie explicite de compatibilité/versionnement. |

Les comptes globaux, `active_season_id`, snapshots anonymes, règles de purge, communications et permissions ne sont pas des candidats au nettoyage de ce lot.
