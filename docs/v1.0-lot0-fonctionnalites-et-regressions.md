## 1. Périmètre et règle d'invariance

- **Même expérience visuelle et interactionnelle que le back-office LinKs**, mais aucune fonction métier LinKs sans usage réel dans Halloween Map.
- **Conserver toutes les fonctions actuelles de Halloween Map**, y compris les actions rares et conditionnelles, les textes simples, les brouillons juridiques, les paramètres et les options de modération.
- Le back-office reste **indépendant** : ses propres données, comptes, droits, API et déploiements. Les futurs « blocs DomotiK Studio » n'introduisent pas de couplage opérationnel à LinKs.
- Phase 0 : pas de migration, pas de suppression de code métier, pas d'édition de `VERSION`, pas de release ni mise à jour `latest`.
- Les indications de tests du tableau ci-dessous sont des **cibles de couverture** ; leur présence dans une suite historique ne prouve pas la couverture précise d'une action sans inspection/exécution du scénario.

La refonte doit traiter explicitement la découvrabilité de **tous** les modules auxquels le rôle connecté a droit sur mobile, sans perdre les usages existants.

## 4. Invariants qui interdisent toute simplification fonctionnelle

- Le serveur fait autorité pour les autorisations, pas la seule visibilité d'un bouton. `SUPER_ADMIN` et `ADMIN` n'ont pas les mêmes capacités. `users.manage` ne permet pas automatiquement de gérer les SUPER_ADMIN.
- `dashboard` utilise la **saison active** ; `houses`/`statistics`/`communications`/`activity` utilisent la **saison consultée**. Les écrans globaux ne sont pas filtrés par la saison consultée.
- Un visiteur peut créer son compte hors saison ; une inscription publique de maison exige **saison active + fenêtre ouverte**. Les administrateurs habilités peuvent créer/éditer hors de ces contraintes ; en absence de saison active, la saison préparée est utilisée selon la règle métier existante. Il ne faut surtout pas déduire l'autorisation serveur de la simple présence d'un sélecteur.
- Carte publique : exige une saison active, y compris lorsque le Super Admin dispose d'outils de préparation en back-office.
- Saisons archivées/purgées : lecture et snapshots ; pas de réouverture involontaire des actions d'écriture.
- Saison TEST : aucun email effectivement envoyé ; les campagnes relatives utilisent leurs ancres (ouverture, fermeture, purge, inscriptions).
- Contenus juridiques : brouillons séparés des versions publiées, conflits `409`, historique immuable, obligations de réacceptation, preuves durables et règles de confidentialité inchangées.
- Les métriques de collecte ne doivent ni être assimilées à des visiteurs uniques, ni devenir des métriques de clics LinKs.

## 6. Risques UX/techniques déjà repérés par inspection du code

| Risque / observation | Impact possible | Consigne |
| --- | --- | --- |
| `components/Admin.tsx` réunit navigation, chargement de données, filtres et actions (plus de 1500 lignes) | Régression en extrayant le shell | Déplacer en premier les éléments **purement visuels** ; conserver les sélecteurs et services ; tests caractérisant les interactions |
| Branches mobile vs desktop distinctes (`if (mobileView)`) | Inaccessibilité ou différence de périmètre fonctionnel | Inventorier les permissions et interactions sur les deux formats ; concevoir un seul modèle de navigation |
| `StudioShell` possède son propre titre et son propre sélecteur de thème `domotik-content-theme`, en plus du thème admin | Double header/thème et collisions de styles | Garder un seul thème et une seule hiérarchie de titre, sans toucher à Tiptap ni aux validations |
| `AdminActivity` charge ses données via sa propre requête ; `Admin.tsx` les charge aussi pour une autre vue | Risque d'invalidation/doublon de chargement | Ne pas changer les critères serveur ; mesurer et dédupliquer seulement après tests de périmètre |
| UI d'administration `PumpkinMark` | Identité incorrecte par rapport à la marque officielle | Utiliser `artwork/branding/halloween-map-wordmark-official.webp` et son app icon officiel, sans toucher au site public |
| Graphiques LinKs en DOM impératif, Halloween en React | Incompatibilité de cycle de vie | Reprendre modèles, tokens, accessibilité et interactions ; UI en composants React |
| `AdminUsers` protège dernier Super Admin, délégations et auto-édition | Risque d'élévation de privilèges si simplification | Conserver les validations serveur et les gardes du formulaire |
| `Campaigns` gère saisons TEST, RELATIVE/ABSOLUTE, ciblage vérifié et retry | Envoi email involontaire, dérive horaire | Conserver le service et écrire les tests d'état/temporisation |
| `DocumentWorkspace` publie des documents juridiques versionnés | Écrasement juridique ou mauvaise réacceptation | Aucun changement de workflow publication sans tests métier dédiés |
